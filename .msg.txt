fix(ranking): prose is not source, and a rare name beats a large file

Re-measuring accuracy on this repository's own questions found it had fallen
from 11/12 to 7/12 in top place, with two causes.

Documentation outranked the code it describes. "where are the scanner's
ignore rules defined" put README.md second and repository_scanner.py third,
because the readme says the same sentence in prose and so repeats every word
of the question with nothing else competing. A context pack is source for an
agent to read; prose about the source is a pointer to it. Documentation and
build files now carry the same penalty tests already did — .md/.rst/.txt,
pyproject.toml, Dockerfile, requirements*.txt, constraints.in. A file is
classified by its extension, so markdown_adapter.py is still a parser.

Size then beat subject. "where are the default config values" put
ranking.py first: it holds all three of {default, config, values} across 361
distinct words, so raw coverage scored 1.0, while config.py — the file the
question names — holds two of them across 104.

Density weighting was tried and reverted: it fixed that pair and broke three
others, because a small file that mentions a word in passing then beat the
file that is actually about it. What works is the name itself: a file whose
name matches one of the question's words wins when that word is rare in the
repository. "config" appears in a handful of files and config.py is named
after it; "value" appears in most of them, so values.py answers nothing
specific. Measured: top-1 went 7/12 -> 8/12 and top-3 11/12 -> 12/12.

_name_answers needed to be an instance method for that — it reads the
document frequencies now — and its single-word case was unreachable, since a
one-word question can never satisfy a two-word floor.

tests/test_ranking_by_file_kind.py pins both, including that only the
extension decides, so a future markdown.py is not mistaken for prose.

339 passed, ruff and mypy clean.
